# Torn Company Training Manager v1.1 Reliability & Audit Design

## Goal

Make training actions materially more reliable, make failures diagnosable, make releases self-consistent, and add a local audit trail without broadening the script into a full company ERP.

## Scope

This release combines the user-approved A + B + C work:

1. **Reliability pass**
   - Replace synthetic mouse-event training with Torn's manually-triggered company training POST.
   - Preserve explicit user confirmation and exact employee-ID targeting.
   - Distinguish Torn acceptance from later API/news verification.
   - Account for Torn API/news cache delay instead of declaring failure after a few seconds.
   - Add a diagnostics/self-test surface that never exposes credentials or session secrets.
2. **Release/changelog/update metadata**
   - Move to version `1.1.0`.
   - Add `CHANGELOG.md`.
   - Add explicit `@updateURL`, `@downloadURL`, and `@supportURL` userscript metadata.
   - Make `package.json` the single version source used by the production build.
   - Fail release verification when generated userscript metadata does not match the package version.
3. **Action/audit trail UI**
   - Persist a rolling local-only audit log of the latest 500 entries.
   - Log user-initiated train/pay actions and their outcomes, plus significant refresh/history/settings failures or changes.
   - Provide an Audit Log UI with filtering, copy/export, and explicit clear-with-confirmation.

## Non-goals

- No automatic or unattended training.
- No background Torn write actions.
- No third-party backend, Supabase, Google Sheets, or remote telemetry.
- No API key, RFC token, cookie, session identifier, or raw authenticated response body in diagnostics or audit storage.
- No stock, advertising, pricing, employee recruitment, or general company-ERP features.
- No mobile/PDA redesign in this release.

## Training Action Architecture

The existing controller remains the policy authority. A training action can only reach page infrastructure after all existing freshness, eligibility, train-count, and action-lock guards pass and the director explicitly confirms the action in the UI.

`CompanyPageActions.submitTrain(employeeId)` changes from synthetic DOM mouse events to a same-origin POST to Torn's company endpoint. The action layer must:

1. Resolve exactly one native Torn employee row/control for the requested numeric employee ID.
2. Obtain the current RFC token from same-page Torn state without exporting or persisting it.
3. POST to `https://www.torn.com/companies.php?rfcv=<token>` with form fields `step=trainemp2` and `ID=<employeeId>`.
4. Use `credentials: same-origin` and `X-Requested-With: XMLHttpRequest`.
5. Parse Torn's response defensively.
6. Return only a sanitized category such as `accepted`, `rejected`, `unsafe_dom`, or `http_failed`; never return credentials or persist a raw authenticated response body.

The script must fail closed if the employee mapping is ambiguous, the RFC token cannot be located, the target is cross-origin, or the response cannot be safely categorized.

## Training State Machine

Training uses these user-visible states:

- `pending`: request is being prepared/submitted.
- `accepted`: Torn returned a success indication for the POST.
- `awaiting_verification`: request was accepted but company-news/API confirmation is intentionally delayed to account for cache.
- `verified`: a new company training-news event for the exact employee ID is observed.
- `accepted_unverified`: Torn accepted the request but no confirming news event appeared after the verification window; retry is blocked until refresh/manual verification.
- `rejected`: Torn explicitly rejected the POST.
- `failed`: transport, unsafe DOM, parsing, or unexpected runtime failure.

`accepted` is never treated as equivalent to `verified` for historical bookkeeping.

## Verification Timing

The controller performs one immediate verification attempt. If the expected new company-news event is absent, it exposes `awaiting_verification`, waits at least 31 seconds, then performs cache-busted verification attempts. The cache-bust uses a unique timestamp query parameter on the Torn API request. A final absence becomes `accepted_unverified`, not `failed`.

The controller must never fabricate a training-history event from the POST response alone.

## Diagnostics

Diagnostics are computed on demand and are not a telemetry system. The UI exposes a collapsible Diagnostics/Self-Test section containing sanitized values only:

- script version
- controller status/stale/error state
- last successful refresh timestamp
- current train count and employee count
- eligible/skipped/next counts
- current action state
- training-history event/unresolved counts
- active pay-dock count
- employee-page detection result
- exact-target row/control availability for the current next employee
- RFC-token presence as a boolean only
- API capability status as known by the controller

`Copy Diagnostics` serializes the sanitized object. API keys, RFC values, cookies, authorization headers, and raw authenticated responses are prohibited.

## Audit Log Model

Storage key: `r4_tcm_audit`.

Container shape:

```json
{
  "schemaVersion": 1,
  "entries": []
}
```

Each entry has:

```json
{
  "id": "<timestamp>-<monotonic/random-safe suffix>",
  "timestamp": 0,
  "type": "train|dock|restore|refresh|history|settings",
  "phase": "requested|accepted|awaiting_verification|verified|rejected|failed|changed|completed",
  "employeeId": null,
  "employeeName": null,
  "details": {}
}
```

Allowed details are deliberately narrow: requested wage, prior wage, restored wage, train count before/after when known, eligibility reason codes, sanitized failure reason, changed setting names, and history rebuild completeness. The log does not store API keys, RFC tokens, cookie/session data, authorization headers, or raw Torn response bodies.

Retention is rolling latest-500; appending entry 501 removes the oldest entry. Audit storage failure must never block the underlying Torn action.

## Audit Events

At minimum, record:

- `train/requested`
- `train/accepted`
- `train/awaiting_verification`
- `train/verified`
- `train/accepted_unverified`
- `train/rejected`
- `train/failed`
- `dock/requested`
- `dock/verified`
- `dock/unverified`
- `dock/failed`
- `restore/requested`
- `restore/verified`
- `restore/unverified`
- `restore/failed`
- `refresh/failed`
- `history/completed` or `history/failed`
- `settings/changed` with changed key names only, except non-sensitive policy values may be included.

## Audit UI

The full manager gains an **Audit Log** button. It opens a modal/panel with:

- newest-first entries
- filters for action type and result/phase
- employee text filter matching name or ID
- Copy Visible Log
- Export JSON
- Clear Log, guarded by explicit confirmation

The global badge remains read-only and does not expose the audit log.

## Release Architecture

`package.json.version` is the single source of release version truth.

`src/userscript-header.txt` uses `__VERSION__` instead of a hard-coded version. `scripts/build.mjs` reads `package.json`, replaces `__VERSION__`, and writes the production userscript. The build also verifies that no unresolved version placeholder remains.

Userscript metadata adds:

- `@updateURL https://raw.githubusercontent.com/R4G3RUNN3R/Torn-Company-Training-Manager/main/dist/Torn%20Company%20Training%20Manager.user.js`
- `@downloadURL https://raw.githubusercontent.com/R4G3RUNN3R/Torn-Company-Training-Manager/main/dist/Torn%20Company%20Training%20Manager.user.js`
- `@supportURL https://github.com/R4G3RUNN3R/Torn-Company-Training-Manager/issues`

`CHANGELOG.md` follows Keep-a-Changelog-style sections, starting with `1.1.0` and preserving historical release notes that can be stated from repository history/current behavior without inventing undocumented detail.

CI continues running tests and production build on every branch. A new release-integrity test checks package version, built userscript version, metadata URLs, and absence of `__VERSION__` in `dist`.

## Error Handling

- All writes remain fail-closed on stale state or unverified eligibility.
- Direct training POST failures are categorized and surfaced visibly.
- Accepted-but-unverified training blocks duplicate retry until refresh/manual verification.
- Audit write failure is non-fatal and reported only in diagnostics, never allowed to cancel a Torn action.
- Diagnostics and audit serializers must redact known sensitive key names recursively before display/copy/export.

## Testing

Tests must cover:

1. Direct training POST exact URL/body/credentials and RFC-token presence.
2. Missing/ambiguous employee target and missing RFC token fail closed.
3. Torn success/rejection response categorization.
4. Immediate training verification and delayed cache-aware verification.
5. Accepted-but-unverified state blocks retry.
6. Audit append, rolling 500 retention, sanitization, clear, and storage recovery.
7. Controller audit events for train/dock/restore and significant failures.
8. Audit-log filtering/rendering and clear confirmation behavior.
9. Diagnostics redaction and expected self-test fields.
10. Build version injection and explicit update/download/support metadata.
11. Existing eligibility, route detection, manager window, settings gear, minimize/maximize, payroll, and global-badge regression behavior.

## Compatibility and Safety

The release preserves current v1.0.6 desktop behavior: exact 24-hour inactivity cutoff, addiction rule, no Train button for ineligible employees, movable/resizable manager, minimize/maximize, gear settings button, global badge, explicit confirmation before Torn writes, and fail-closed stale-data behavior.
